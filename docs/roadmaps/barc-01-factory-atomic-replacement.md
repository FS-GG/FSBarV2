## Outcome and route decision

Implement a **HighBar-owned Recoil extension** that performs one authoritative compare-and-replace of one factory's complete production queue. A valid request replaces an actually nonempty queue with exactly N requested production orders, cancels its unfinished old build with the selected engine's metal-refund behavior, preserves Repeat and rally, and reports a correlated commit or refusal. It must never expose a partially cleared/repopulated queue. Rejected preconditions perform no replacement or build cancellation. A lost result remains unknown.

Use the existing owned engine-patch/build/custody route. A pure synced Lua gadget is **not sufficient** on this engine: its command array iterates independently vetoable commands and has no rollback/result guarantee. An unsynced AI Lua message is not an authenticated synced transaction. Adding a native atomic Lua primitive would still require the same engine transaction plus game ingress and outcome machinery; the direct typed AI route is smaller for the existing HighBar consumer. Keep the BAR game unchanged for production; extend the private fixture only for setup/observation and fault qualification. No arbitrary custom command, undocumented modifier, fixture-only mutator or upstream write is assumed.

The existing v1 browser, guest, native protobuf messages and per-child Count1 contract remain frozen. The new API is an explicitly versioned **engine dependency**, not a claim that an unknown command already works in 7555. Required positive nonempty Replace remains open until this route passes real engine acceptance; safe refusal is an interim safeguard.

## Native contract to implement

### Scope, bounds and capability

Atomicity is **per factory**; multiple actors retain independent outcomes. The linearization point covers the complete production queue, its tags/count bookkeeping, old active-build detachment/cancellation and refund accounting. Observers may see the old state or committed new state. Callback effects initiated after commit are subsequent game actions, not grounds to report rollback. Admission logging of an attempted command is not a queue mutation.

Initial supported installation is the existing controlled Linux x86-64 headless BAR profile with the pinned game/content/mod-options and a new exact engine/plugin pair. Native transaction count is bounded by64; initially advertise factory Count4 after Count1/2/4 acceptance, with total broker children still<=64. Queue comparison accepts at most64 complete entries and a fixed total request cap (proposed16KiB); excessive parameter payload refuses rather than truncates. No arbitrary requested command ID/options/parameter array exists in the API: only a positive allowed definition and bounded count. Old queue tuples are comparison evidence, never replay instructions.

Append new C ABI surface after existing rally fields; preserve their positions. Probe old stable engine version callbacks first, then a size/version/capability query, before reading an appended pointer. New capability reports ABI1, request/result structure sizes and limits. Extend exact supported-engine identity matching to retain the old rally engine and recognize the new combined engine. Never accept a version prefix or read an unknown table to discover whether it is long enough.

No per-policy capability bit exists in frozen v1. Therefore the broker's reviewed supported-profile mapping must bind the exact new **actual runtime** engine identity in `TacticalCataloguePage.content.engine_version` to atomic replacement support; HighBar reports that identity only after its native probe succeeds. Preserve content-bound catalogue revision and refuse unknown/legacy identities for nonempty Replace. `kEngineReleaseId` is currently a configured pin, not automatically a runtime probe: make the equality between configured artifact pin and real engine callbacks a checked condition before publishing the identity. Do not overload descriptor native_command_id or a numeric bound as a hidden feature bit.

### Minimal typed API and state

Working names below describe new implementation, not available7555 symbols:

1. `FactoryReplacement_GetCapabilities` and `FactoryReplacement_ReadSnapshot`: bounded read-only callbacks. Snapshot returns factory native control-lifetime token plus complete `(type,id,options,tag,timeout,float-bit params)` entries. HighBar computes the existing v1 hash from those exact entries and caches the binding to its actor lifetime/basis/catalogue. The engine compares full entries at commit, not only the non-cryptographic v1 hash. A monotonic native token changes on unit creation/reuse and team-control transfer; maintain it in UnitHandler/Unit state and serialize it with engine state. Overflow disables the extension; it never wraps into an old identity.
2. A typed `SFactoryProductionReplaceCommand` appended to CommandTopic, handled by Engine_handleCommand. It contains native actor token, exact expected queue, definition, count, deterministic latest simulation frame, authority-fence epoch, AI operation sequence and bounded request identity/digest. Callback AI identity/team/host are derived from the live engine context; callers cannot choose another team. The callback validates and sends a dedicated bounded synced packet. Authentication means the engine/server registered host, AI instance and team, with HighBar as a trusted native adapter; it does not claim isolation from a malicious library in the same engine process or a malicious AI host. A successful send means Submitted only.
3. A narrow `SFactoryReplacementFenceCommand` carries arm/renew/revoke epoch changes for this extension. The same authenticated synced path installs/removes permission. This closes the in-flight revocation ordering seam without changing browser messages. HighBar retains its existing wall-clock checks; engine uses deterministic frame expiry and serialized fence state. Revoke is ordered, not retroactive: an operation committed before the revoke barrier remains committed. A revoke acknowledgment must not claim the barrier settled while prior operations/fence delivery remain unknown.
4. `FactoryReplacement_ReadResult` queries a typed per-AI bounded result record: operation identity, exact request digest, committed/refused disposition and reason, authoritative frame, before/after queue evidence, cancellation/refund summary and exactlyN new tags on commit. Queries never mutate synced state. Store dedupe/high-water and a deterministic bounded recent-result ring in simulation state; no client-local acknowledgment may change synced capacity. Same operation/same bytes replays the result, different bytes refuses; an evicted old sequence cannot execute again. A missing/expired result is Unknown, never inferred refusal or success.

Use fixed-width integers and explicit network serialization, not float parameters for64-bit identities or a platform memory-layout dump. New network message/topic numbers are allocated and tested as part of this patch; none is presumed supported today. Treat ABI size constants/generators and engine sync/version identity as part of the build. A different engine version must refuse joining the qualified match. Verify the actual sync-version value changes: GameVersion.cpp GetSync uses SPRING_VERSION_ENGINE, while the additional suffix is appended only by GetFull; setting VERSION_ADDITIONAL alone is not proof of peer incompatibility.

### Authoritative prepare/commit/notify

Implement `CFactoryCAI::ReplaceProductionQueue` as a staged engine-thread operation:

- **Validate/prepare:** authenticate active AI and fence; reject expiry, actor-token/ownership changes, incomplete/mismatched current queue, non-factory, disabled/unavailable definition, bad count and unavailable result capacity. Reapply native build-option and game command policies with a strict error path. Prepare every new Command with options0, new tags and all counters before mutation; do not use multiplier flags. Use the fixed engine-derived production recipe, not caller-supplied positioning. Audit the pinned factory-applicable BAR hooks; a veto/error means refusal. If a hook changes the target, revalidate and refuse against that changed state rather than overwriting it. This does not authorize rollback of unrelated gadget side effects.
- **Commit:** after all fallible preparation, enter a short no-callout/no-allocation block. Swap the prepared complete production deque, tag counter and build-option counts; detach the old active buildee, reset pending build state, perform cancellation/refund state transitions, and record Committed. Cancel old wait/dependency bookkeeping exactly once. Refactor cancellation so no script, destruction listener, native callback, UnitCmdDone listener or queue observer can run between destructive steps. Do not invoke current StopBuild before this point. Preserve `newUnitCommands` and Repeat byte-for-byte.
- **Notify:** only after consistent state is installed, emit required cancellation/icon/script notifications and permit normal SlowUpdate. Reentrant commands cannot enter the middle of the commit. If a callback subsequently destroys or reorders the factory, the prior transaction is still Committed; retain its authoritative commit evidence. Never report it refused after mutation.

Replacement intentionally cancels an unfinished active order even if its definition equals the new requested definition; allN requested items are new orders. Refund only invested metal using engine accounting, including storage overflow behavior, with no energy refund. A completed already-existing product is preserved and excluded from new-product counting. Preparation refuses safely if consistent cancellation state cannot be established. This needs real observer/reentrancy tests; a deque swap alone is insufficient.

Keep current authority, catalogue and monotonic deadline checks immediately before submission. The engine fence/frame expiry adds an authoritative check. Do not pretend a simulation-frame expiry equals wall-clock expiry during network delay or a paused simulation; paused commit refuses in this initial profile, while unresolved sends remain Unknown under existing broker deadlines. No unsynced local clock may drive divergent simulation outcomes.

## HighBar/FSBar integration without widening v1

Add a bounded `FactoryReplacementAssembler` for typed Replace children. Key by complete binding/channel/basis plus parent/input identity. Buffer all declared child indices (max64), retain attribution in the internal queue entry, reject missing/duplicate/conflicting children and inconsistent action/catalogue/policy/actor definitions, and enforce the earliest deadline. Do not begin a replacement before the complete parent is validated; reconstruct each actor's N from its Count1 children and enforce the broker's common per-actor count and current negotiated bound. Each actor group becomes one native transaction with N tags mapped back to its original child indices. Per-factory atomicity does not turn a multi-actor parent into an all-or-none game transaction.

Recheck every member's fence under the existing live dispatch gate, acquire external control, then recheck actual queue/token after that acquisition and submit exactly once. Acquisition may itself change the queue; never silently rebase the observation. Route completed engine results to the existing native dispatch event stream for every original child. Emit Applied only after Committed; Refused maps to existing skipped/refusal statuses with bounded details. Submitted/pending does not emit Applied. A timeout or process/channel loss remains unknown; only same-identity query/replay is allowed, not a new replacement request.

After native capability and integration gates pass, FSBar's factory predicate permits nonempty Replace only for the reviewed new identity, while retaining safe refusal on old/unknown engines. Raise actual advertised Count to4 through the negotiated bound. Append retains the safety recipe/options0. Do not merge this adapter into source paths while the safety owners edit them; join their protected results first.
